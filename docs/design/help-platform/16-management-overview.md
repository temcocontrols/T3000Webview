# Help Platform — management overview

## What the reader and the author see

A **published documentation site in the style of Microsoft's MSDN / Learn**: one searchable portal covering
every product, one page per topic, snapshots per release, and an **online editor** — a page can be opened,
corrected and published from the browser, with the same "edit this page" path leading back to the source in
git. Authors who prefer a desktop get the identical editor, and the identical AI, inside VS Code.

That site is not a new invention to be trusted blindly: it is generated by the same class of engine Microsoft
built its own documentation on, which is why it needs no bespoke software from us at all.

The single source that feeds the site also produces the offline **CHM** that ships with each installer, so
nothing about the customer's experience depends on a website being reachable. And the logic is ours: content,
rules and AI live in our code and in git, while the editor shell itself is software we never have to build,
maintain or pay for.

## Requirement by requirement

| # | Requirement (in the words of management) | How it is met | State |
|---|---|---|---|
| R1 | A long-term help system, not another tool we outgrow | One source of Markdown in git, one publishing engine, one registry. No proprietary format to migrate off. | Built |
| R2 | AI keeps it organized and up to date | Local AI reads each commit, summarises it, finds the pages it affects, drafts the edits and lists what is still owed. | Partly built, finishing in phase 2 |
| R3 | The developer does not manage docs per repository | Developer only writes the commit message. The platform does the documentation work and routes it to the maintainer for approval. | Built for summaries; page drafts in phase 2 |
| R4 | Tied closely to T3000: every commit summarises itself and updates the docs | A commit summary pass already runs over the history. The same pass gains "which pages this commit affects". | Built |
| R5 | We keep what we have today (annotated screenshots, context help, offline CHM) and add AI on top | Same content, same CHM artifact, same F1 map — plus the web hub, versions, search and the AI layer. | CHM pipeline unchanged |

Two boundaries matter, and they are deliberate:

- **The platform is internal.** It runs on the maintainer's PC. It is not part of a customer installation
  and does not require T3000 to be running.
- **Only artifacts ship.** A customer installation receives the CHM (and the F1 map inside the app). No
  editor, no AI, no authoring tooling, ever.

## 2. How one commit becomes updated documentation

Read each column as one participant; time runs top to bottom. Only two people ever act — the developer who
commits, and the maintainer who approves.

```
  developer            git              PLATFORM (local AI)          maintainer      outputs
      │                 │                        │                        │             │
      │ commit          │                        │                        │             │
      ├─────────────────►                        │                        │             │
      │                 │ trigger                │                        │             │
      │                 ├────────────────────────►                        │             │
      │                 │                        │ [1] summarise change   │             │
      │                 │                        │ [2] find pages         │             │
      │                 │                        │ [3] draft page edits   │             │
      │                 │                        │ [4] list pages owed    │             │
      │                 │                        │                        │             │
      │                 │                        │ ready to review        │             │
      │                 │                        ├────────────────────────►             │
      │                 │                        │ approved               │             │
      │                 │                        ◄────────────────────────┤             │
      │                 │ doc commit             │                        │             │
      │                 ◄────────────────────────┤                        │             │
      │                 │                        │                        │             │
      │                 │ publish                │                        │             │
      │                 ├────────────────────────┼────────────────────────┼─────────────►
      │                 │                        │                        │ CHM · web   │
      │                 │                        │                        │ · PDF       │
      │                 │                        │                        │             │
      │ nothing to do   │                        │                        │             │
```

| Step | Who | Effort for the developer |
|---|---|---|
| Write the commit | developer | none — they already do this |
| Summarise, map to pages, draft edits, list gaps | platform (local AI) | none, automatic |
| Approve or correct the prose | named page owner (default: documentation maintainer) | minutes |
| Publish CHM / web / PDF | platform | none, automatic |

The important guarantee, stated for management: **the AI proposes, a human disposes.** Nothing reaches a
customer without a named person approving it, every change is a git commit that can be reverted in one
command, and the AI never has publish rights.

## 3. Many products, many repositories, one help system

```
  build time — one source, many outputs

   products/*/docs ──┐
                     ├──►  PLATFORM  ──► web hub        (all products, one search)
   shared/glossary ──┘              ├──► CHM  T3000     (only T3000 pages)
                                    ├──► CHM  firmware  (only firmware pages)
                                    ├──► PDF  per release
                                    └──► F1 map per app (page id -> help topic)
```

Rules that keep this manageable as the number of products grows:

1. **Content never moves.** A product's pages stay in that product's repository, next to the code they
   describe. Adding a product to the hub is a mapping entry, not a content migration.
2. **One search over everything.** The hub indexes all products together; each installer only carries its
   own product's pages.
3. **Federated ownership.** Each product's pages have their own owner; the maintainer owns the platform and
   the cross-product pages.
4. **Cross-product links are explicit.** Where a firmware page should link to a T3000 page, the link is
   declared so the hub can resolve it and the offline CHM can degrade it to plain text.
5. **Per-release snapshots.** Documentation is snapshotted with each release, so a customer on an older
   build can read the documentation of their build.

## 4. Many devices without duplicated pages

```
   one page, many device models — text is written once

   registry entry:  "PID Control" ──► variants:  T3-TB    T3-NB    T3-LB    T3-BB
                                                    │        │        │        │
                                                    └────────┴───┬────┴────────┘
                                                                 ▼
                             rendered once per variant; shared sentences reused
                             (edit the shared text once, all four variants follow)
                             (variant-only text lives in a clearly marked block)
```

A device model is a **variant of a page**, not a new page. That is what prevents the current situation from
being recreated at three times the size once more products arrive.

## 7. The AI, and why it runs locally

- The model runs **on the maintainer's PC**. No cloud service, no API keys, no monthly bill, no
  documentation text leaving the building, and it works in a room with no internet.
- Model weights are downloaded once and stored on disk; models with permissive licences (Apache / MIT) are
  preferred so the installer is never restricted by licensing.
- Guardrails: draft-only, no publish rights, every suggestion is a normal git change, prompts are versioned
  in the repository, and the choice of model is a setting — not something baked into the platform.
- Because the model is a setting, we can move to a different or larger model later without redesigning
  anything.

## 9. Risks and how each is contained

| Risk | Containment |
|---|---|
| The AI writes something incorrect | Draft-only; a named human approves; everything is a git commit; one-command rollback |
| Documentation drifts again in a year | The commit pass lists the pages still owed; CI reports it; the health report shows it per area |
| A key person leaves | Content, registry and rules live in git; approving is the only manual step, and any engineer can do it |
| Model licensing limits distribution | Permissive models only, recorded in the registry with their licence |
| Confidential material leaving the building | Local model, no egress, no keys; the platform is internal |
| The platform itself becomes a maintenance burden | Build an extension, not a fork, until a branded installer is genuinely needed; the publishing engine is pinned, not patched |

## 10. What this does not change

- The developer's workflow. Nobody is asked to write, format or review documentation unless they want to.
- The customer-facing artifact: the **CHM** ships exactly as it does today, and F1 help is unchanged.
- The location of the pages in the repositories.
- What a customer installation contains: the CHM, and nothing else from this platform.
- The publishing engine decision: pinned, patchable, replaceable.

## 11. Decisions requested

1. **Name the documentation owner** — one person accountable for the platform and for approvals.
2. **Approve the platform as internal tooling** — it runs on our machines, and only its outputs ship.
3. **Approve VS Code as the shell** — an ordinary editor plus our extension, with a branded installer left as
   an optional packaging step later.
4. **Approve the local-AI approach** — offline models, no cloud, permissive licences only.
5. **Approve per-product publishing** — each installer carries only its own product's help pages.
6. **Approve the phase order** above, or re-order it.

## Relationship to the other documents in this folder

Written after the initial design pass, this document assumes two corrections to it:

- **The platform is a standalone internal application.** It does not run as a page served by the T3000
  runtime, and it does not require T3000 to be installed. This supersedes the hosting placement recorded
  as locked decision 11 in `README.md`, and the hosting assumption in `15-online-editor.md`.
- **The engine and the platform are separate checkouts.** The publishing engine keeps the "pin first, patch
  last" policy; the platform is the thing we own and extend.

Everything else — the content model, the registry, the CHM artifact, the review rules, the AI guardrails —
is unchanged by that correction.
